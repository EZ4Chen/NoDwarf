# 居民人格与记忆调研

调研日期：2026-10-29。范围：本机 RimTalk 1.4.4、SillyTavern 官方文档、RimTalk 记忆扩展的作者说明，以及 NoDwarf 当前工作区。本文为设计建议，不代表功能已实现；本轮不修改游戏代码或既定版本计划。

结论：借鉴 RimTalk 的事件记忆和 SillyTavern 的上下文组织，但 NoDwarf 的人格必须影响实际行动。首个目标应是“被某人照料 → 留下相关经历与关系变化 → 下次在条件允许时优先帮助对方”，沿用版本计划 0.6 的验收方向。

实施更新：同日后续已完成结构化记忆、规则归档、相关观察、离线照料偏好及受校验居民 AI 首版，详见[开发版本计划](开发版本计划.md)。下文“当前缺口”为研究当时的基线，不能替代最新交付状态。

## 2. RimTalk 本体如何做

### 2.1 人格与状态分开

`Hediff_Persona` 保存人格描述；`PersonaService` 支持根据人物背景生成描述，也有预设人格路径。组织对话时，再加入当前心情、思想、关系、技能、健康和场景等信息。人格描述相对稳定，当前饥饿或伤势不会每次改写成新人格。

### 2.2 由真实事件生成结构化记忆

`MemoryHookService` 对接思想、事件记录、互动、救援、伤害等游戏信息。`MemoryEntry` 包含对象 ID／名字、事件键、权重、发生时间、最近回忆时间、备注、重复次数、视角，以及指令、创伤、里程碑等标记。发起者和承受者可以得到不同评价。

`PawnMemoryTracker` 按“对象 + 事件类型 + 视角”合并重复记录；部分事件不累计权重，其他事件按时间窗口折算。普通寒暄等事件被排除，避免反复聊天挤满重要经历。普通记忆上限为 25 条；创伤最多 3 条；里程碑对每个对象最多 3 条，不能把 25 理解成所有类别的总上限。

记忆功能代码默认关闭；这是可启用能力，不能仅凭安装本体就判断玩家正在使用。

### 2.3 遗忘、检索与防复读

普通记忆的权重按半衰期衰减，太弱的条目会被清理；实现提供随权重／类别变化的半衰期计算。里程碑不按同样方式衰减。最近刚回忆过的事件会降低检索分，减少总提同一件事。

组装对话印象时，按类别选取少量内容：最多 5 条指令、3 条创伤、2 条个人经历；针对交谈对象选重要记忆 2 条、近期记忆 2 条，并另有里程碑选择与冷却。这是相关性筛选，不是把整个存档交给模型。

两点值得调整后再借鉴：

- 本体在构造提示词时就标记部分记忆已回忆。NoDwarf 更适合在结果被采纳后再记录使用，避免失败请求影响下次检索。
- 重要事件可以降低谈论频率，但决策仍应知道其存在；“少提起危险”不能变成“忘了危险”。

### 2.4 上下文缩短不等于长期总结

`TalkHistory.EnsureMessageLimit` 按 `ConversationHistoryCount × 2` 限制历史消息条数，默认值 2 对应最多 4 个消息项。历史格式化可保留说话者与台词，去掉多余响应字段；`BuildCausalSummary` 主要提取事件标签、主题或意图，并非递归调用模型总结人生。`PromptService` 还会按详细／简短级别减少人物信息。

因此，本体主要使用：**有限近期历史 + 人物状态精简 + 相关事件记忆**。界面中叫“ConsolidateNow”的功能，英文显示为“Prune Faded”，不能据此认定存在 LLM 分层摘要系统。

本地核查入口（反编译工作文件不随仓库分发）：

- `RimTalk.PawnMemory/MemoryEntry.cs`：权重、时间与持久化。
- `RimTalk.PawnMemory/PawnMemoryTracker.cs`：合并、筛选、上限、衰减清理。
- `RimTalk.PawnMemory/MemoryHookService.cs`：事件入口和默认开关。
- `RimTalk.Data/Hediff_Persona.cs`：人格与记忆提示词组装。
- `RimTalk.Data/TalkHistory.cs`、`RimTalk.Service/PromptService.cs`：历史裁剪与上下文组织。

## 3. 分层总结来自哪些扩展

| 项目 | 作者说明中的做法 | 对我们的启发 |
| --- | --- | --- |
| RimTalk Expand Memory | 四层架构 ABM → SCM → ELS → CLPA；结构化标签；按时间、重要性和相关性注入；支持总结、归档和清理 | 长期存储与每次注入分开；先有结构化事件，再组织摘要 |
| RimTalk Lucid Chronicle | 当天原始记录 → 当天短期摘要 → 每日摘要 → 长期记忆；中期超限时把较旧部分并入长期记忆；支持固定记忆、日记、人格补充 | 给事件按时间分段；重要经历可保留；人格变化采用有来源的补充 |

Lucid Chronicle 还记录台词对象与人物身份，提供过去台词作为说话风格样例；人格补充默认需要手动生成。作者明确说明其记忆实现与 Expand Memory 不兼容。以上是独立扩展能力，不归入本机 RimTalk 本体的已验证实现。[Expand Memory 作者页](https://steamcommunity.com/sharedfiles/filedetails/?id=3608181242)、[Lucid Chronicle 作者页](https://steamcommunity.com/sharedfiles/filedetails/?id=3749797638)。

分层压缩能控制长度，但不是无损记忆。若长期只把“旧摘要 + 新摘要”再摘要，遗漏和误解可能逐渐累积。我们的摘要应保留原事件引用，以便重新生成和纠错。

## 4. SillyTavern 如何做

| 组件 | 作用 | 适合借鉴的部分 |
| --- | --- | --- |
| 角色卡 | 描述、人格、场景等进入提示词；首句和示例影响表达风格 | 少量稳定人格事实，搭配简短说话样例 |
| World Info／Lorebook | 按关键词等条件取出相关条目，受优先级与上下文预算控制 | 只注入当前人物、地点、任务涉及的知识 |
| Summarize | 对聊天历史生成摘要，可按消息数等条件触发；保存摘要状态并支持编辑、回退 | 把旧对话转为可追溯的阶段摘要 |
| Chat Vectorization | 把历史消息转为向量，根据近期内容找回相关旧消息 | 大量自由文本积累后，补充语义检索 |

角色卡和世界书本身并不会自动把所有游戏事件变成经历。需要应用层决定哪些事实属于谁、何时写入和何时取出。[角色卡官方文档](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)、[World Info 官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)。

Summarize 是额外的模型请求，可能丢细节或产生偏差。其主 API 模式可用旧摘要和新增消息生成新摘要，并控制触发条件、输入范围和输出长度。[Summarize 官方文档](https://docs.sillytavern.app/extensions/summarize/)。

特别注意：Chat Vectorization 中的“先摘要再向量化”旨在改善检索；命中后仍插入原消息，并不直接缩短聊天历史。旧 Smart Context 已被标为弃用，当前应参考 Chat Vectorization。[向量化官方文档](https://docs.sillytavern.app/extensions/chat-vectorization/)、[旧 Smart Context 状态](https://docs.sillytavern.app/extensions/smart-context/)。

## 6. 构建小人人格需要什么

### 6.1 六类数据各负其责

1. **稳定人格**：例如谨慎程度、社交倾向、责任感；数值与描述来自同一份权威数据，逐项对应可执行选择。
2. **偏好和目标**：喜欢的现有活动、擅长／想学的工作、一个当前长期目标。目标需要完成条件和放弃条件。
3. **当前状态**：饥渴、伤势、疲劳、心情、所在环境。来自即时模拟，不从旧摘要推测。
4. **人际关系**：对谁有好感、信任或亏欠，以及支持这个判断的事件。先复用现有好感，不一次引入大量关系数值。
5. **亲历记忆与认知**：知道什么、怎么知道、何时发生；把事实、传闻和主观解释分开。
6. **表达风格**：用词、句长、直接或委婉，加少量范例。它负责让人物说话有区别；行为差异由前五项及行动规则共同体现。

人格变化应缓慢、有来源。例如连续受到照料后更信任某人，可以新增关系认识；一次普通争吵不应彻底改写核心性格。由模型生成的“人格补充”先作为候选解释，不能直接覆盖事实与全部性格参数。

### 6.2 最小记忆结构建议

```text
WorldEvent：事件 ID、时间、类型、行动者、对象、位置、实际结果
ResidentMemory：记忆 ID、所属居民、引用事件 ID、视角、情绪倾向、重要性、
                来源（亲历／目击／听说）、告知者、首次／最近时间、重复次数、最近使用时间
MemorySummary：涵盖时间段、引用事件／记忆 ID、版本、摘要内容
ResidentGoal：目标类型、对象、状态、完成条件、期限、来源
```

事件在行动真正结算后写入，按 ID 去重。对话中的“我会给你送饭”创建承诺候选；送达食物以后才生成完成事件。私人交谈只进入参与者或可听见者的认知；传闻不把内容自动升级为世界事实。

不同人物可以对同一事件有不同感受，但世界结果只有一份。概要中“他救过我”必须能追到对应事件；“我相信他”是主观评价，两者分开保存。

### 6.3 每次怎样组上下文

```text
真实事件 → 居民可知范围 → 结构化记忆／关系更新
                                   ↓
稳定人格 + 当前状态 + 当前目标 + 相关人物／记忆 + 少量近期对话
                                   ↓
模型提出有限行动 → 本地校验与执行 → 实际结果成为新事件
```

检索先用人物 ID、任务、地点和事件类型筛选，再按相关性、重要性、时间排序，并限制同类重复项。先做结构化检索即可；自由聊天规模增大以后，再加入向量检索帮助发现语义相近的旧内容。

上下文设置独立 token 预算，预留输出、规则和工具描述，再分配状态、人格、关系、事件和对话。按实际模型统计 token，不把中文字数直接当 token。超限先裁普通重复对话，保留当前危险、目标和重要事实。预算不等于必须填满。

世界书中的通用知识也受人物知识范围限制；开发 Wiki 不直接作为每个居民都知道的事实。记忆文本和外部内容均是数据，不能改变工具白名单与执行规则。

### 6.4 压缩与遗忘策略

- **重复合并**：日常重复事件合并次数与时间范围，保留重要变化。
- **分级保留**：普通活动可衰减、归档；救命、重大损失、未履行承诺等有更强的保留策略。
- **分段摘要**：达到条数／token 阈值后，在后台总结已结束的对话或时间段。无新内容时不反复总结。
- **保留依据**：摘要保存事件引用、版本和覆盖区间；可从归档事实重建。原始日志也设保存策略和磁盘预算，不能无限积累。
- **纠错优先**：即时世界状态优先于旧摘要；已完成目标不能反复执行；姓名变化仍用稳定人物 ID 关联。
- **情绪与事实分离**：悲伤可以缓解，死亡事件仍然成立；感激不必永久保持同一个数值，救援经历仍可被检索。

### 6.5 让游戏继续稳定运行

按有意义的事件、空闲机会或决策冷却触发模型，不每个 tick 给每个居民发请求。饥渴自理、危险撤离等继续由本地规则及时执行。限制并发、单次步数、会话成本和请求频率；超时或离线时保持可玩的规则行为。

异步结果返回时重新检查观察版本和行动条件；角色死亡、工作被取消或资源已被占用时不能执行旧决定。执行成功后的回执与事件一起去重持久化，读档不重复结算。

调试界面显示“本轮用了哪些事件、提出什么动作、是否采纳、实际结果”，足以定位行为问题；无需生成长篇内心独白。

## 7. 建议实施顺序与验收

以下细化现有 0.6 方向，未修改版本计划，也不把所有高级功能列为首次接入前置条件。

| 顺序 | 工作 | 可观察验收 |
| --- | --- | --- |
| 第一阶段：记得并行动 | 复用照料事件，补事件引用／重要性；观察接口输出相关关系与记忆；接通受校验决策 | 被甲照料过的乙，在两名同伴需求和可达性相当时更倾向帮助甲；能看到实际行动与结果 |
| 第二阶段：稳定差异 | 少量有玩法对应的人格偏好、目标和表达样例；近期对话窗口 | 两名性格不同的居民在多次相似情境下呈现稳定选择差异，同时都遵守紧急自理与危险避让 |
| 第三阶段：长期连续性 | 归档与阶段摘要、重要事件保留、目标更新、存档迁移 | 大量普通事件后仍能找回救援经历；读档保持关系与目标，不重复完成承诺 |
| 后续按需要 | 语义检索、人格成长补充、日记和聚落编年史 | 检索准确性、事实一致性与请求开销确有改善，再扩大规模 |

必要回归场景：同一事件重放不重复加好感；私聊不泄漏给未参与者；承诺与完成分开；摘要错误可追溯和重建；同名居民不串记忆；断网能继续生活；过期模型响应不执行；1000 条普通活动不会挤掉已保护的重要事件。模型行为用固定场景多次观察，数据去重、权限范围与版本校验使用确定性检查。

第一阶段做成后，小人才真正具备“因为记得过去，所以这次选择不同”的表现。对话、摘要和日记再围绕这条行为链逐步丰富。
