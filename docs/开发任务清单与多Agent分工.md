版本：0.1 · 2026-10-23

当前执行范围已收缩为“林间工坊”可玩 Demo：建设、居民施工、功能判断、锻造和蓝图复用。下文保留为长期备忘，不要求按全部阶段先建设框架；优先试玩并依据反馈修改 Demo。

## 2. 第一阶段：先约定公共接口

这一步由一个集成负责人主导，完成后才能安全拆分核心实现。接口先覆盖原型，不建设通用大框架。

- [ ] A01 确定坐标、楼层、尺寸与物件 ID：格子、墙边、家具占地、朝向、操作位的表示。
- [ ] A02 确定世界状态、玩家命令、变化事件与表现层读取接口。
- [ ] A03 确定 tick 边界、系统更新顺序、资源预约与冲突处理；只有提交阶段修改共享世界。
- [ ] A04 定义最小数据内容：墙、地板、门、炉、铁砧、原料、成品、工作室条件；使用稳定命名空间与 ID。
- [ ] A05 明确目录与文件责任、测试入口、日志格式、合并顺序及引擎版本。
- [ ] A06 确定首轮基准机器、地图／人数场景与性能记录字段；FPS、TPS、内存、LLM 延迟和费用分开记录。

验收：三个实现者能基于同一套定义独立制作地图、界面和人物模块，接口变更有单一负责人。文字约定与可编译的数据契约一致。暂不要求跨平台位级确定性。

## 3. 第二阶段：可操作的功能房间

目标：拖墙、放门、摆设备、显示工坊能力。使用占位素材，先让建设有操作感。

| ID | 任务 | 依赖 | 建议负责范围 | 验收 |
| --- | --- | --- | --- | --- |
| B01 | 小地图、格子／墙边占地、局部变更查询 | A01–A04 | 地图模拟 | 放置／拆除正确改变状态 |
| B02 | 相机平移缩放、楼层过滤、鼠标选取 | A01–A02 | 场景与输入 | 高低层选取无歧义 |
| B03 | 地形与构件绘制、预览及无效位置提示 | B01–B02 | 场景与输入 | 预览与提交位置一致 |
| B04 | 家具朝向、占地、操作位及放置检查 | B01、A04 | 地图模拟 | 不重叠，操作位可查询 |
| B05 | 手动划定功能区、封闭房间辅助识别 | B01、B04 | 房间规则 | 能容纳室内与露天工作区 |
| B06 | 工坊条件与能力判断 | B05 | 房间规则 | 显示具体缺项；改建后局部更新 |
| B07 | 工具栏、选中信息、建设／取消操作 | B03、B06 | UI | 玩家能完成操作并理解失败原因 |
| B08 | 基础存读档：构件、区域、ID、tick、种子 | B01、A02–A04 | 数据与存档 | 读档后布局与状态一致 |

可并行：B01 与 B02 使用公共坐标契约分别开工；B06 可先用手工区域数据开发；B08 可先针对状态契约写序列化。B03、B07 等集成任务须等待依赖。

阶段验收：从空地建出工作室，摆放炉与铁砧，系统显示其实际能力；拆掉设备后反馈正确；保存再读档保持一致。

## 4. 第三阶段：居民真的完成工作

目标：一个居民抵达工作位，用原料完成加工；再把建筑保存并施工为蓝图。

| ID | 任务 | 依赖 | 建议负责范围 | 验收 |
| --- | --- | --- | --- | --- |
| C01 | 居民状态、位置与移动命令 | A01–A03、B01 | 人物模拟 | 独立于画面运行 |
| C02 | 基础寻路与地形变更后的路径失效 | B01、B04、C01 | 人物模拟 | 门／障碍变化后正确重规划 |
| C03 | 物品、库存、预约与搬运 | A03–A04、C01–C02 | 工作与生产 | 两人不能取得同一份原料 |
| C04 | 工作任务、操作位预约、取消与恢复 | B06、C03 | 工作与生产 | 任务有原因、不会永久卡住 |
| C05 | 一条加工配方与工坊使用 | C04 | 工作与生产 | 真实消耗与产出，可查停工原因 |
| C06 | 蓝图数据、范围保存与放置验证 | B04–B08 | 建筑蓝图 | 自建布局可保存、预览及重新载入 |
| C07 | 蓝图生成施工／搬运任务 | C03–C04、C06 | 建筑蓝图＋集成 | 有材料和劳动消耗，不瞬间复制成品 |
| C08 | 分层纸片角色与动作事件 | A01–A02、C01 | 表现与素材 | 朝向、走路、工具、遮挡正确 |

可并行：人物寻路、蓝图数据、纸片角色分别开发；生产模块使用固定地图与假移动执行器先测规则。蓝图接入真实施工在任务系统稳定后完成。

美术任务：先定义正／背／侧模板、尺寸、挂点和图层顺序；验证一套衣服与工具，再扩展素材。AI 生成初稿需清理和对齐，不直接批量生成未经验证的角色包。

## 5. 第四阶段：尽早证明 LLM 的核心价值

LLM 接口与评估可在第二、三阶段并行研究；实际行为接入依赖任务、事件和存档契约。不可一直推迟到游戏做完才加对白。

| ID | 任务 | 依赖 | 建议负责范围 | 验收 |
| --- | --- | --- | --- | --- |
| D01 | DeepSeek 适配、明确关闭思考、结构化结果 | A02、A05 | LLM 服务 | 配置可替换，密钥不入源码和日志 |
| D02 | 异步调度、并发／费用上限、超时与取消 | D01 | LLM 服务 | 不阻塞模拟；有限重试 |
| D03 | 最小人格、认知、记忆、关系与承诺 | A02、A04 | 人格与社交 | 事实与主观记忆分离 |
| D04 | 事件到上下文的选择、结果命令校验 | D02–D03、C04 | AI 接入 | 过期／无效结果不能改世界 |
| D05 | 工坊需求或扩建提议 | B06、C06、D04 | AI 接入＋UI | 形成可预览、修改和批准的工程 |
| D06 | 两人协商分工或履行承诺 | C04、D03–D04 | 人格与社交 | 不同人格产生可见行为与关系后果 |
| D07 | 模型结果与请求状态的存档记录 | B08、D04 | 数据与存档 | 读档不重抽已经采纳的决定 |
| D08 | 延迟、无效率、过期率、加速与费用评估 | D02、D04 | 验证 | 输出测量数据，不用感觉判断 |

联网实测必须单独记录供应商、模型和参数；离线假响应可测接入正确性，不能作为真实模型效果证据。API 调用具有费用，运行前明确凭据来源与测试预算；没有凭据时先完成不依赖联网的工作。

第一版闭环：玩家建工坊 → 居民加工 → 出现实际需求 → LLM 提出可执行方案／协商分工 → 玩家干预 → 任务与承诺留下结果 → 保存并继续。

- [ ] P05 验证暂停／加速、读档、长时间运行、集中取消任务和最坏合法负载。

P01 可与 B/C/D 实现并行；P03 须基于契约和测量，不让多个 Agent 各自发明一套线程调度器。多线程边界从首期设计，多线程收益需要实际证明。

## 8. 多 Agent 分工方式

### 工作原则

1. 一名集成负责人维护接口、主场景、工程配置和任务状态，其余 Agent 负责界限明确的模块。
2. 公共接口先定到足以开工；变更通过负责人协调，不能各自修改同一个类型。
3. 同一文件同一轮只归一个 Agent。美术导入、Godot 自动生成文件与场景修改也计算在内。
4. 一个任务一次交付一个可编译、可验证结果。禁止顺手重构无关系统或引入新技术栈。
5. 多 Agent 并行不等于游戏多线程；前者是开发协作，后者是运行时架构。
6. 集成后验证模块交互；各分支分别通过不等于合并后通过。

### 建议目录（待创建，不代表当前已有模块）

```text
source/
  Contracts/              # 集成负责人维护公共数据与接口
  Simulation/
    World/                # 地图、占地与变更
    Rooms/                # 区域与功能条件
    Agents/               # 居民状态与移动
    Jobs/                 # 工作、预约与执行
    Production/           # 物品、配方与生产
    Blueprints/           # 蓝图与施工规划
    Social/               # 人格、认知、关系与承诺
    Persistence/          # 存档
  Services/LLM/           # 适配、队列与结果校验
  Presentation/           # 相机、渲染、纸片动作与 UI
  Content/                # 设备、配方、功能条件及翻译
  Assets/                 # 统一规范的图像与素材
  Scenes/                 # 集成场景与模块演示场景
```

实际目录随接口阶段确定，避免只为凑目录拆大量空模块。已有 `Scripts/Main.cs` 由集成负责人逐步拆分，不让所有 Agent 同改。

### 适合当前四个并行席位的安排

先用一个负责人完成 A01–A05，再开启：

| 角色 | 第一轮 | 第二轮 | 第三轮 |
| --- | --- | --- | --- |
| 集成负责人 | 契约维护、入口与合并 | 集成建设、存档与验证 | 集成任务、蓝图与 AI |
| Agent A：模拟 | B01、B04 地图与设备 | C01–C02 居民与寻路 | C03–C05 工作与生产 |
| Agent B：表现 | B02 相机与选取 | B03、B07 建设 UI | C08 纸片角色与动作 |
| Agent C：规则／服务 | B06 功能规则，先使用固定区域 | B05／C06 区域与蓝图数据 | D01–D02 云端服务，然后接入 D04 |

以上是建议轮次，不要求一位 Agent 永远负责同一领域。依赖未就绪时，使用同契约的固定测试数据或模块演示场景；不能声称已经集成，也不能为绕过依赖另造正式世界模型。

### 合并规则

当前尚未初始化 Git。正式多人／多 Agent 编码前建立仓库与可回退基线；是否使用独立 worktree 按实际协作环境决定。不要在尚未选择许可证时把本地开发误当成对外开源。

涉及相同模拟状态或工程配置的改动顺序合并，冲突由负责人处理。独立模块可以并行实现；依赖升级、接口变更与最终集成不能无协调地并行执行。

验收顺序：构建 → 对应模块检查 → 集成场景 → 必要的性能／双平台检查。只有出现新改动、失败或未解决风险才扩大重复测试，不让每个 Agent 对全部项目重复跑相同检查。
