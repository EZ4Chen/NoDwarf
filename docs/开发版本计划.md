## 配置驱动与 Mod 扩展约束（2026-10-30，持续推进）

后续结构重构以配置驱动和 Mod 扩展为验收要求。本节保留完整目标与实施约束。生产／生物统一加载、补丁、依赖及模块存档首批已接入，具体边界见上一节；事件定义、更多内容领域、性能与发布验收仍继续推进。

- **内容与参数由定义管理**：物品价值、材质、品质、装备属性、方块耗料和耐久、掉落、作物生长、配方、物种、事件条件与效果参数、叙事节奏与提示模板逐步迁入类型化定义。原版内容也走同一加载入口。物品 ID 不得分别在估值、生产、界面和事件白名单里维护多份。
- **执行能力通过注册表扩展**：保留寻路、物理、库存事务、存档提交等 C# 执行器；定义引用稳定的能力 ID 并组合已有条件与效果。新材料、新配方、已有能力下的新事件不应要求修改核心分支。全新机制通过明确的处理器接口注册，未实现能力在加载阶段拒绝，不能仅凭配置字段假称支持。现有开发控制台 Lua 不直接充当正式 Mod 行为接口。
- **统一加载协议**：提供模组清单、ID、版本、依赖、兼容范围和确定的加载顺序；定义使用命名空间，保留既有 ID，迁移使用明确别名。新增与覆盖采用显式补丁，重复 ID、依赖循环、缺失引用及冲突应指出来源文件和字段。不得依赖启动进程的当前工作目录偶然找到配置。加载全部校验成功后一次发布，失败保留原目录。
- **配置与性能一起设计**：启动或载入世界时解析并交叉校验，将定义编译为不可变目录、稠密索引、缓存曲线和已解析处理器。每 tick 不读 XML/JSON、不做反射查找；字符串 ID 用于编辑与存档，热点使用已解析引用。世界及后台任务持有明确的目录版本，禁止原地修改共享定义。先实现启动加载；热更新另行限定可改范围和失效规则。
- **LLM 与事件共用定义**：已加载事件的参数 schema、允许值、工具描述和本地执行校验来自同一目录。Mod 新增已有执行能力的事件后，叙事者可以发现并调用；模型不能越过已注册能力、事件预算或模拟线程复核。连接密钥与付费请求额度仍由统一 AI 服务和玩家设置管理。
- **存档绑定内容版本**：保存启用的 Mod 清单、版本、加载顺序、稳定定义 ID 及必要的语义指纹。纯名称、翻译、贴图变化与身体结构、行为等语义变化分别处理。缺少 Mod 或不兼容变更时先诊断并提供明确迁移途径，不静默删除实例或重置状态；迁移失败保留原存档。

首批顺序：统一定义目录与加载校验 → 物品/价值/配方单一数据源 → 事件与叙事策略注册 → 逐步迁移方块、作物及其他内容。性能缓存修复可独立推进，不等待整个 Mod 框架完成。

验收必须提供独立示例 Mod：不改 C# 新增铜矿、铜锭、加工配方及引用铜锭的物资发现事件，能够展示、生产、估值、被叙事者发现并实际执行，存读档后保持一致。另验证补丁冲突、依赖循环、缺失 Mod、旧 ID 迁移、仓库外启动，以及 100 人场景和批量定义加载的性能。优先完成这条闭环，再扩大可配置范围。

## 项目审计与修改方案（2026-10-30，分批实施）

本轮按“先检查、最后给方案”执行，未修改业务代码。审计覆盖模拟与任务分配、导航与地形后台计算、人物渲染缓存、存读档、定义加载、生产与估值、生物兼容、LLM 事件调用、测试和导出链路。结论来自静态追踪、独立复现和无窗口检查；不是完整玩法平衡、全量安全审计或 GPU 性能验收。工作区同时有生物与相机改动，本方案按检查时的代码描述，保留其他工作的修改。

### 按依赖分批实施

每批单独验证并形成可审查变更；下列是实施要求，完成情况与实测数据见本节末尾的批次记录。

**第 1 批：补基线并修复明确的重复计算。**

- 将本轮复现固定为回归场景，建立统一检查清单；先补齐检查工程资源及仓库外启动，随后提取无 Godot 依赖的模拟核心项目，避免每个工具各编译一套源码和资源。

- 验收：不变任务不重复排序；增删／优先级变化立即生效；居民改装、转向仍正确；100 人循环转镜头在容量足够时不反复合成同一组合，稳定后内存不持续增长。比较 tick 耗时、分配量和长帧，不能仅看平均 FPS。

**第 2 批：统一定义加载和存档版本基础。**

- 采用类型化定义，不做万能键值字典。拆分表现、玩法语义指纹；语义摘要按解析后的规范字段生成，避免 XML 属性顺序／空白无意影响兼容。每个世界持有自己的目录版本，后台任务也携带相同标识。
- 为存档加入启用包清单、版本、顺序及必要的定义修订；保留旧存档读取与旧 ID 别名。缺失内容或语义不兼容时列出原因，迁移在副本上完成，成功验证后才切换世界。重命名／换贴图无需迁移身体和物品状态。
- 将在制任务绑定到创建时的配方修订；投入、产出和工作量必须一致。删除旧修订只能经显式迁移或可恢复的拒绝载入处理。
- 验收：名称修改可读档、身体结构修改要求迁移；旧配方任务不凭空增产；缺失 Mod、冲突、循环依赖、未知能力和非法资源路径均得到可定位诊断；仓库内外加载同样内容得到同样目录。

**第 3 批：统一物品、价值和生产，并完成第一个数据 Mod。**

- 物品定义首先收拢价值、材质／品质、用途、食用与装备属性；估值、生产、界面与事件白名单都读取同一目录。先保持原版行为等价，再扩展新内容。
- 方块／工位分离稳定内容 ID 与执行类别，先保留旧枚举适配与存档迁移，不一次性重写地形存储。新增已有采矿／冶炼能力下的矿物和配方应只需配置。
- 事件目录引用已注册条件／效果处理器，统一生成 JSON schema、工具描述、允许值及静态校验；执行时仍检查库存、落点、难度预算和当前世界。叙事策略和提示模板可配置，玩家连接设置不受其覆盖。

比较方法：同一进程、相同当前数据、相同 JSON 排版，保存预热后取 7 次中位数；原路径基线是世界 JSON 再嵌入会话 JSON，新路径为安全快照复制。两列都只计保存时的主线程工作，不含后台总耗时，不能当成 FPS。最终整合当前配置清理后的 100 人、20,049 堆物品场景：49.197 → 6.627 ms，分配 45,073,640 → 5,811,440 字节；后台编码与刷盘另为 32.852 ms。此数据替代开发中途不同配置版本的计时。

新增 `save` 离线检查与 `session-async` 无窗口集成检查，并将 `equipment` 换装检查接入统一清单。覆盖快照隔离、连续保存、备份、编码／提交失败、队列恢复、已完成快照释放、保存中退出、当前格式读档、过期结果丢弃及装备索引生命周期。验证日志在 `source/.local/save-*`、`source/.local/checks/{save,session-async,equipment}.log`。

边界：安全快照复制和最终场景节点／界面切换仍在主线程；没有声称完全消除所有长帧，也未将无窗口结果当作 GPU 或实际 FPS 验收。未调用真实模型或修改玩家存档。

## 0.5 最小范围：第一场近战

目标是一次可复现的小规模冲突，先让现有铁剑和人物健康系统产生玩法。默认用现有 3 位居民，对付 1–3 名敌对人形单位；提供明确的测试袭击入口，开局不自动突袭，不先做完整敌军导演。

1. **征召与指挥**：选中居民后征召，支持移动、指定攻击和停止；解除征召后回到工作／作息。切换时安全处理原任务、材料预约与携带物，不复制或丢失资源。
2. **最小攻击规则**：只做徒手与铁剑近战，使用现有实体装备、战斗技能和护甲减伤；攻击范围、冷却、命中／伤害规则明确。伤害通过现有健康入口结算，不另造第二套血量系统。
3. **敌人和三维通行**：敌对单位不会加入居民工作表或领取生产任务；从有效地图边缘进入，走合法坡道／楼梯接近目标。墙体、楼板和高差阻挡攻击，不能隔墙或隔层命中；不可达时显示状态并限频重试。本版没有攻城破墙。
4. **反馈与战后恢复**：显示敌我、目标、攻击动作／受击提示和受伤状态；失能或死亡立即停止战斗并释放目标。复用现有护理与休息，先支持原地护理，不把担架、专属医疗床或完整俘虏系统列为必需。死亡装备若转为地面物品，只结算一次；全员失能时给出明确结果。
5. **暂停、存档与性能**：攻击冷却及敌人逻辑由模拟 tick 推进，不跟随 FPS；暂停不攻击，倍速正确推进。保存阵营、征召、目标、冷却与必要随机状态，读档校验目标，不重复造成伤害或掉落；寻路不每帧重新搜索。
6. **护理补给**：保留原地护理；护理者没有随身绷带时，可预约并实际取用公共库存，再前往伤员处。缺料、断路、取消或伤员死亡时释放预约，显示具体原因，不凭空治疗。同一伤口不被多人重复消耗物资。
7. **平民避险**：提供玩家指定的集合点与手动警报；未征召居民暂停普通任务，安全交接预约／携带物后前往集合点。警报期间不重新领取外出任务；集合点不可达或没有安全补给时明确提示。解除警报后重新检查任务再复工，不恢复过期目标。本版不做复杂活动区编辑器或自动战术评估。

分两步集成，但不另外铺开大版本：先实现单个居民与单个测试敌人的移动／攻击／失能，再接 3 对 1–3 的测试袭击、护理与复工。LLM 不计算命中或逐帧操纵敌人；未来通过受校验的高层命令参与决策。

**验收场景：** 从现有生产链造出并装备铁剑，手动触发一次袭击，征召居民迎击；至少覆盖平地近战、隔墙与隔层拒绝命中、楼梯接敌、失能停止攻击、战中保存恢复，以及解除征召后的材料守恒和复工。增加“医生背包无绷带、公共仓库有绷带”与平民警报集合场景，分别验证缺料／断路反馈和解除警报后的复工。记录该场景 TPS／FPS，不能只看动画是否流畅。战败也应可理解、可读档，而不是出现卡死或任务永久占用。

**本版不做：** 远程弹道、复杂掩体、阵型、骑乘、攻城、外交与战争地图、捕俘，以及魔法／斗气。这些不影响本版验收，不为它们提前搭建庞大框架。

### 0.5.1 最小范围：生存与照料

健康扩展已接通：疾病分阶段病情与独立免疫条、营养不良、失血展示、严重骨折／烧伤的永久损伤及存读档。已补统一状态定义与视图、分阶段的意识／移动／操作／疼痛效果、治疗质量与有效期、手动及自动疾病护理和到期续诊；仍保留 10 个身体部位。伤口感染有实际触发，热病暂供开发测试；现已补热病接触传播与隔离、严重疾病／营养不良的宽限及致死规则；专用药物仍未加入。具体规则见 `source/README.md` 的“健康进度、免疫与后遗症”。

**已补第一批：** 满载安全卸货、单份口粮预约、紧急自理打断、手动吃饭取粮、独立照料工作与失能伤员喂饭、不可达／缺粮原因、预约取消与存读档。已补营养不良分阶段积累、持续吃饱恢复及失能影响；已追加致死宽限、全局粮食预警与可支撑时间估算；12 人双层医院补给长局已通过，开放布局和全气候平衡仍待试玩。

以下保留 0.5.1 已交付功能的验收约束，供新机制接入后回归；不是重新排期。

- **致死规则依赖可靠的自理保障。** 普通工作／研究、个人拾取、交流、治疗等活动在危急饥饿／疲劳时，应按既有规则让路与恢复。负重已满且无随身口粮时，先安全交接或放下非必需货物，再取食；不能先因负重拒绝取粮、又永久保留原搬运负重。治疗中的短动作可以在明确的安全节点中断，不能无期限延后自理。
- 自用取粮与给伤员送饭共用可取消的短期预约。缺粮时按本次所需取用，避免沿用普通拾取一次取走最多 5 件的规则，让多人饥饿时前一个人囤走全部口粮；取不到时释放目标并限频重选，不空跑或争抢同一份。
- 持续饥饿采用独立、可保存的暴露／衰弱进度，不把饱食降到 0 直接视为瞬间死亡。明确宽限、恶化、失能、最终死亡与恢复条件；玩家应能在恶化前看到原因和可采取的行动。
- 同时区分没有食物、食物不可达、已被预约，以及居民无法自行取食。照料任务使用真实公共口粮，避免个人物品和公共库存重复计数；多名护理者不能重复喂同一需求。
- 将基础送饭与专业治疗的资格分开：启用照料工作的普通居民也能喂饭，不因唯一医生忙碌而让伤员饿死。按断粮／伤势紧迫程度选择照料对象，再比较可达性与路程；先用本地明确规则，不等待 LLM 决定。
- 粮食预警分别显示可直接吃的口粮、待加工原料和个人携带量，原料不能冒充现成饭。提供按当前人数与近期消耗估算的口粮可支撑时间，并明确估算不包含未来收成；对“总量充足但某居民不可达”另行提示，能定位人、粮和断路原因。医疗缺料提醒同样区分现成绷带与待加工布料。
- **验收：** 固定三人场景中制造短期断粮，预警后补给能恢复；持续不处理会按规则恶化。加入一名无法行走且没有随身口粮的伤员，另一人取粮喂食后能够恢复。补充满载搬运者取食、研究暂停恢复、三人同时饥饿且仅有三份公共口粮的场景；分别覆盖无护理者、缺料、断路、取消、失能期间与恢复期间存读档。先验证公共粮食可用时不会因调度／负重问题长期挨饿，再验证断粮死亡。
- 长局同时记录饥饿见底时长、衰弱程度、公共与个人可达食物、护理等待和死亡原因，不能只以无人死亡判定平衡。后续按用户要求已追加饮水、气温伤害与食物腐败，旧的无这些规则的长局记录不作为新版生存平衡证据。

### 0.5.2 最小范围：仓储与生活质量

**生活部分已有基础：** 自动床位归属、卧室条件与有限心情效果、餐桌椅用餐、篝火／棋桌休闲及同伴收益、拆除设施后的保底行为均已接入。剩余重点是仓储容量、供应控制和新增安全连接；手动分配私人床位可后置，不重新开发家具。以下按优先级表先交付安全连接，再交付仓储，最后做联合试玩。

- 为物品定义堆叠／占容规则；库存、搬运中的货物和已预约目的地共同遵守容量。仓库满时停止继续向该格派送并提供原因；拆仓、取消、读档或旧档超容量不能删除物资。旧档溢出须有可见、可搬走的过渡处理。
- 生产工作位也须有有限的输出缓冲。新批次开工前检查或预约落料空间；加工中失去空间时按明确规则等待输出，不重复扣料、重做成品，也不无限堆到工坊脚下。已落地成品仍由现有搬运工作清走，不把新增产出凭空放进全局库存。
- 在现有补产目标上增加关键原料最低保留量及允许使用它的用途。保留量只约束新预约，不追溯吞掉已搬运／已投入的材料；明确人工覆盖入口与后果，避免所有配方互相等待。
- 增加单个物品堆的禁用／恢复，供玩家保护物资或阻止去危险位置取物。禁用不是删除；堆场不接收某类物品也不等于禁止生产使用它。统一约束生产、自动取食／照料和搬运；已有预约须安全释放或完成明确的交接，携带中的物资不能消失。保留量与禁用导致口粮／医疗品不足时明确说明，玩家可定位并解除。
- 将总量、可用量和占用原因分别呈现：个人持有、任务预约、在途物资及专用医疗储备不能都算作自由原料。延续已有库存目标补产语义；以后增加条件订单时，明确区分“维持库存目标”和“本轮制作数量”，多项启动条件须同时满足。0.5.2 不引入完整条件编辑器。
- 保留已有床位归属、用餐与休闲设施，复核仓库／门禁变化后的可达性。房间品质、露天／地板休息、用餐条件形成有上限的心情影响；保留低效保底，重复事件不能无限叠加。暂不做复杂私人财产、贵族住房要求或几十种娱乐需求。
- **验收：** 小仓库与工坊输出区装满后无丢失、超额预约、无限堆放或反复扣料，扩仓／清运可恢复；制衣达到保留量后停止，绷带仍能使用允许的布。禁止使用一堆已预约物资后，原任务安全交接且后续任务不再领取，解除后恢复。改善同一居民的住房／用餐条件后，心情原因与数值同步变化，拆除设施或换床后正确更新。上述状态保存后继续一致。

### 0.5.2 新增安全与食物调度验收

- **采掘水患（P1-1）**：对即将贯通水体或承压含水层的挖掘暂停相关任务，提示位置、风险和继续／取消入口；覆盖侧壁、上方与下方、楼梯及批量开挖，不只检查平面邻格。未知区域只提示开挖处可察觉的湿润／渗水风险，不显示未发现水体全貌。风险继续变化或读档后重新校验，不能把一次确认变成所有后续挖掘免检。涨水导致站位或路径失效时停止普通作业，释放预约，优先沿仍合法路径撤离；无路时定位受困者并提供可达救援／排水处理入口，不虚构安全路径、不瞬移。**验收：** 挖穿蓄水池侧壁与顶板、受压涌水、取水岸边涨水、撤离中断路及存读档；不重复刷警报，也不新增没有救助手段的溺水致死。
- **门禁（P1-2）**：先实现通行／锁闭，不引入钥匙、阵营权限或自动开关动画链。锁门／拆门触发导航失效，重检已有路径、材料预约、病床和餐位；门格被居民占用时拒绝锁闭并说明原因，不把人挤进墙。物理房间边界与通行许可分别判断；普通门默认不水密，界面明确用闸门挡水，现有闸门继续保持水量守恒。**验收：** 唯一出口被锁后显示断路，解锁恢复；在途取料、救援与读档均不穿锁门、不丢物；锁门不凭空排水。
- **安全作业范围（P1-3）**：首版复用跨层选区能力，只做作业范围、禁止通行范围与停止外出取料开关，不另建复杂区域编辑器。候选工作、材料来源、站位、完整路径、医疗救援和返回集合点均校验；两个区域间的道路经过禁行区时不能因终点合规而放行。没有安全食物／水／床位时提示缺项和位置，人工放宽需明确后果；不能让居民反复领取后又取消同一任务。保留紧急撤出危险区域的受限出口规则，征召与手动命令的例外单独校验。**验收：** 区内工坊需要区外原料、区内两点之间路径越界、警报期间喂饭／送水及解除限制复工；供应不足可定位、取消释放预约，限制状态存读档一致。
- **临期食物（P1-6）**：在现有到期时间与预约上加入临期优先，先筛可达性、使用权限和保留用途，再比较到期时间与路程，不能追逐远方将过期物而让居民饿死。进食、送饭和烹饪取料复用候选规则；搬运只为有效目的地派单，不为临期排序反复倒仓。已预约原料过期后沿用现有取消／退料规则，重新选料。**验收：** 两批不同日期口粮、较旧批次被禁用／断路、取料途中腐败、原料加工中到期、拆堆合堆及读档；过期时间不被搬运刷新，新旧批次不合并丢失属性。保存设施后置，当前固定腐败无需等待新机制才提供调度保障。

上述新入口保留必要表单标签、可访问名称、状态与后果提示；清爽界面不能省略“为何停工”和“恢复后会发生什么”。

### 0.6／0.7 的连接与后续边界

### P2 扩展的最小交付与验收

这些条目补充上表 P2 边界，属于 0.6 首次接入后的可选增量；不新增一串必须先完成的版本。冷热暴露与固定期限腐败已有实现，本次不扩大为完整热传导、相变和燃烧系统。

1. **医疗清洁与饮水深化（顺序 11—12）**：保留已有有限水源、水桶、送水、脱水、救援、床位、夹板和义肢。新增医疗用途区域及专用物资限额，再补清水／清洁用品与伤口清洁流程；已有感染继续沿用当前治疗，不能为了增加工艺链先削弱现有救治。现有热病隔离是暂停社交／公共娱乐并排除接触传播的规则开关，允许工作就医；若改为空间隔离，必须同批加入病区活动范围、允许照料者及食物／水／护理供给，并明确替换旧语义。通用储水与水质是后续增量，先有安全水与净化途径，再增加污染伤害，不默认酒精依赖。**验收：** 隔离区唯一水源断路能提示并恢复，照料不越过禁行规则；清洁实际耗材，取消不重复耗用；储水转移量守恒，病床与在途伤员读档不重占；旧档不因新增物资要求突然失去基础护理。

2. **遗体与废弃物（顺序 13）**：保留死者身份与死亡原因，将遗体和遗物关联起来；搬运、安葬与普通原料搬运分开配置。亲近同伴失去居民可产生有限的记忆／心情效果，已有尸体不每 tick 重复触发。腐败食物和破损物品需要接收点及清运入口；永久清除必须明确提示后果，不能靠“移出库存统计”假装清走。**验收：** 死亡、搬运、安葬和读档全过程遗物只出现一份；无墓位／无清运位置时可定位处理。

3. **农业与应急食物（顺序 14—15）**：季节作物表先控制下一次播种，不销毁在田作物；结合本项目温度／日照显示停长与大致成熟窗口，天气不确定性要可见。种植技能先提供有上限的产量收益，产量结果及其对应的播种能力记录随作物保存，不能读档重抽或收割前换人刷收益。继续采用当前收获返种规则，不为贴近 DF 改成必须吃掉／酿造作物才返种；当前也没有强制轮作的必要。应急采集只做一种实际资源，明确成熟量、耗尽与再生／季节限制；可生食与必须加工的原料分开，采集返种作为一种断种补救，商队补种在 0.7 接上。**验收：** 跨季换种不丢在田作物，停播后仍能收获；相同条件下熟练种植的收益可解释；采完一片资源后不能原地无限刷粮，恢复种源后能重新播种。

4. **供应、订单与燃料（顺序 16—18）**：指定料仓要区分“优先这里”和“只许这里”；严格模式下配方所需的全部原料／燃料／容器都要被覆盖，循环供应不能造成物品来回搬运。容器先支持单层装载、有限容量及内容物级预约，领取一份种子或绷带不能锁住整桶其他物资；容器自身、内容物和携带重量不可重复计数。条件订单先做输入余量、产出不足和空容器条件，所有条件同时满足；工坊选择、并行数和在制产量一起限制，已有库存目标仍保留简单入口。木炭先只有一条明确转换配方和适用工序，不把所有炉子／篝火燃料混为一类。食品保存先选一种可解释的方案，腐败与品质、穿用磨损分开结算。**验收：** 两台工坊共享少量原料时不超额预约；只链接矿石却未链接燃料时准确停工；取消容器搬运不吞物；使用木炭后守恒且不消耗厨房保留木料；存档恢复后不重复产出。

5. **品质、餐食差异与磨损（顺序 19—20）**：先给少量成品定义三档品质，给餐食保留配方／主要原料类别，分别连接有限的装备效率、用餐心情或交易价值；金属原料、木料和所有中间品不必一起扩展品质。复用已有品质／耐久属性及堆叠判等，补充配方来源，并复核分堆、搬运、预约、穿戴和存档：同名不同品质／配方／磨损的物品不能合并后丢属性，旧物品赋默认正常品质与完好状态。磨损先从衣物穿用做起，库存待用不一律按穿用速度老化；自动补产与换装应认出可用备用品，旧衣退回明确位置，不让背包越换越满。工具／武器是否因使用或战斗损耗另行校准，不照搬 DF 数值。**验收：** 好坏两把同名工具经分堆、运输和读档仍保持差异；不同餐食偏好有可观察的有限效果；衣物损坏前能补产换装，缺替换品时预警且不凭空生成，旧档不会一加载就集体报废。

6. **个体需求与长期压力（顺序 21）**：先从现有交流、工作／技能成长、休息活动抽取少量偏好；每项需求必须已有实际满足途径，不先塞入无法执行的祈祷、家庭或动物需求。普通娱乐可被工作打断，紧急恢复活动有有限保护，但进食与安全撤离仍优先。压力只由已发生的事件和明确的时间衰减累计，短期心情、长期压力与工作专注分别说明；重要事件按类别／对象去重并限制记忆规模。先提供休养、减少工作、与同伴交流等可恢复后果，复杂失控、精神疾病和暴力连锁不进入首版。**验收：** 两名偏好不同的居民面对同一活动有可解释差异；反复读档／重新观察不会重复增加压力；恢复措施可在有界时间内改善状态，LLM 只能选择行动，不能直接宣告压力归零。

7. **任务控制与道路偏好（顺序 9—10）**：任务优先级只在有资格、可达且满足材料／安全条件的工作之间比较；危急自理、撤离与救援保持更高层级。复用已有区域取消与生产订单启停，补单任务／选区暂停、恢复及紧急程度，不把居民工作偏好改成同一字段。等待信息汇总同类原因并可定位，避免取消日志淹没通知。交通偏好只增加合法路径代价，不使锁门／深水／禁行格变为可通行，也不要求同时实现踏草或道路施工。**验收：** 紧急修门相对普通施工可提前执行，暂停／恢复不重复扣料、不丢携带物；无法执行的高优先任务不饿死其他可执行工作；两条跨层路径按偏好选择、断路后改走合法路线，记录搜索开销与缓存失效，存读档保留设置。

### 0.7 贸易与迁入的补充范围

- **商队访问**：先做一种友好商队与一处交易点，步行运输即可，不要求三格宽马车寻路。到达前检查地图入口、交易点和离场通路，记录访问 ID、停留期限及到达／交易／离开状态；暂停和读档不重置期限。没有通路时给出取消或等待原因，不能无休止原地重寻路。
- **备货与成交**：出口货物先预约并运到交易点；私人物品、禁用物资、医疗／口粮保留量默认不出售。来访货物在成交前属于商队，不进入聚落可用库存或生产取料。先按物品基础价与明确交换规则报价，显示数量、双方得失和运输余量；确认时复查物资与报价版本，只转移一次货权，买入后再实际搬回仓库。撤单、超时、断路或交易点被拆时释放未成交预约，已成交物品保留真实归属，不把商队落地物品自动当作免费资源。
- **有限的外部变化**：交易完成及商队安全离场后更新一条关系／访问记录；先提供简短的下次采购意向或供应摘要，不承诺尚未运来的货。用一次缺种／缺布的进口和一次剩余成品出口验证贸易价值，不先做议价技能树、文化禁忌、贵族禁运或全世界动态市场。
- **迁入与接待**：先做少量成人，接纳前显示人数、主要技能、可见伤势／携带装备，以及当前口粮与床位承载情况。设置可修改的人口上限，达到上限暂停新邀请／接纳，已有居民不会被删除；已接纳在途人数占用名额。新居民由有效入口抵达集合点，再获得唯一居民 ID、工作／作息默认值和床位分配，携带物只登记一次。拒绝、取消来访或入口断路均有明确状态，不通过开发者启用居民入口代替迁入。
- **验收**：至少覆盖报价后货物被占用、超过载重、商队期限届满、成交后尚未入库时存读档；分别检查未成交退回和已成交货权。迁入覆盖接纳／拒绝、达到人口上限、路上存读档与集合点失效；不能重复到访、重复生成装备或让未抵达者先参加生产。儿童成长、家庭迁徙和驱逐居民均后置，尤其不把“拒绝新来者”混同为驱逐现有居民。

**跨版本试玩目标：** 三名居民经历一次粮食紧张、一次小规模冲突与伤员照料，再接纳一名新居民；玩家能通过生产、住房、工作安排和补给恢复聚落。每次失败应有可理解的原因与处理入口。性能、双平台与自由布局长局验收继续保留，不因新增机制而宣称已通过。

## Z 轴怎么做

这里的 Z 轴是玩家理解的“高度／楼层”。Godot 场景使用 Y 向上，当前代码 `Cell(X, Z)` 中的 Z 是水平纵深；模拟层拟使用 `Cell(X, Z, Level)`，渲染时把 Level 映射为引擎高度。玩家界面只显示“第几层”，无需理解引擎坐标。

0.2 就引入包含楼层的格子标识，统一建筑、任务、人物、蓝图和选取坐标，但生成内容先以地表为主。底层预留逐层地形／空间表示，不能把“每个水平位置只能有一个高度”的地表高度表当成最终世界模型。

0.3 按最新决定采用 1 米立方体素和 1.4 米矮人；房间通常保留两格净空。地基顶面定义 F0，默认层高 3 米，＋／－按楼层定位。完整多层操作包括挖空空间、实体楼板、楼梯与屋顶／覆盖判断。当前层可操作，上层隐藏或淡化，下层保留必要轮廓；始终明确预览和施工所在层。寻路优先通过合法坡道／楼梯跨层，也允许有净空的向上一米翻越／向下两米以内跳落，自动任务要求安全返程，超过两米的意外坠落造成伤势，房间按层判断，封闭地下室要有顶部覆盖。

初期采用简单支撑限制，拒绝明显悬空的建设；不引入连续刚体物理或大规模坍塌。世界用格子表达，不等于视觉必须做成 Minecraft 方块风。

## 每版共同遵守的规则

1. 每版交付一个可玩场景、简短操作说明、对应规则检查和已知限制；不以写完框架代替验收。
2. FPS 与 TPS 分开记录。基础频率改为 60 TPS（3× 目标 180 TPS），记录实际 TPS、tick 耗时／积压、帧时间与内存；不把画面流畅当成模拟性能良好。
3. 从 0.2 开始使用固定种子、地图大小和人数做基准；后续增加负载时保留旧场景对照。办公本目标需最终在明确型号的 Windows 笔记本与 M 系列 Mac 实测，当前小 Demo 不构成性能保证。
4. 模拟与画面保持分离。后台生成／寻路读取独立数据，结果由模拟统一校验提交；不让工作线程修改场景树。先测热点，再做必要的并行计算，多 Agent 开发不等于游戏运行时多线程。
5. 新内容逐步采用稳定 ID、外部数据和本地化键，先保留可扩展入口；完整脚本模组工具另行安排。
6. 0.4 加带版本号的存档；此前明确是临时试玩局。0.6 保存已采纳的模型决定，避免读档后重复执行或重新抽取。
7. LLM 请求有预算、超时、状态提示和有限重试；断网时已有任务继续运行，新 AI 决策明确等待。真实接入需要凭据和确定的测试预算，假响应测试不算模型实测。
8. 每版尽量验证两个目标平台；未实测的平台明确标注。导出可分发版本及双平台验证应在 0.5 核心 Demo 阶段完成，签名和商店发行另列。
9. 新机制接入存档时保留物资、人物与任务状态；旧档升级不得静默丢物，也不得因新增饥渴、腐败或损耗规则立即触发不可挽回的惩罚，须明确迁移与宽限策略。
10. 界面先去除冗余说明，再检查初次使用是否仍清楚下一步及其结果。必要表单标签、可访问名称和危险／不可逆操作的后果提示必须保留；缺料、满仓、断路、无人照料等状态要有简短原因及可定位入口。

## 多 Agent 怎么拆，保持简单

每版最多一个集成负责人加两个模块 Agent；没有可独立交付的工作就不强行并行。先约定该版必需的坐标和数据接口，再开工，同一文件同一轮只有一个负责人。

| 版本 | 可并行的两条工作线 | 必须统一集成的部分 |
| --- | --- | --- |
| 0.2 | 地形生成规则；地形显示与鼠标选取（先用固定高低地形） | 楼层坐标迁移、通行、建筑落点与现有 UI |
| 0.3 | 挖掘／楼梯／跨层路径；楼层切换与遮挡 | 跨层任务、房间与蓝图 |
| 0.4 | 采矿搬运生产链；存档（先约定状态结构） | 预约和在途任务恢复 |
| 0.5 | 战斗状态／伤害结算；征召 UI／攻击反馈（先用固定测试单位） | 阵营、三维接敌、任务／物资交接、战中存档 |
| 0.6 | 云端请求与结果校验；人格记忆及可观察的行动反馈 | 模型决定进入任务系统及读档 |

其余版本到开发前再拆。每个模块交付写清允许修改的文件、输入输出、验收步骤与限制；集成负责人维护主场景和共享类型。正式并行改代码前建立可回退的 Git 基线，不代表公开开源。
